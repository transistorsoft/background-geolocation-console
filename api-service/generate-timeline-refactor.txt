  (/dashboard/:org/partials/locations). The handler funnels into
  buildDashboardData (pkg/web/server.go:380-488), which fires this sequence:

  What every poll currently does

  #: 1
  Call site: services.ListCompanies → ensureCompany (services/public.go:117,
    services/services.go:262)
  SQL emitted: SELECT … FROM companies WHERE company_token=? FOR UPDATE
  Notes: row-locks the company
  ────────────────────────────────────────
  #: 2
  Call site: …same ensureCompany
  SQL emitted: UPDATE companies SET updated_at=? WHERE id=?
  Notes: write on every poll
  ────────────────────────────────────────
  #: 3
  Call site: ListCompanies final
  SQL emitted: SELECT … FROM companies WHERE company_token=? ORDER BY id
  Notes: redundant; we already have it
  ────────────────────────────────────────
  #: 4
  Call site: services.ListDevicesInRange (services/public.go:187)
  SQL emitted: SELECT … FROM devices … ORDER BY EXISTS(SELECT 1 FROM locations 
  …)
    DESC, (SELECT MAX(recorded_at) FROM locations WHERE 
    locations.device_id=devices.id) DESC NULLS LAST, id
  Notes: two correlated subqueries per device row — this is the dominant cost on

    tenants with many devices
  ────────────────────────────────────────
  #: 5
  Call site: …same, in-range flag pass
  SQL emitted: SELECT DISTINCT device_id FROM locations WHERE device_id IN (…) 
    AND recorded_at BETWEEN ?…?
  Notes: could fold into #4
  ────────────────────────────────────────
  #: 6
  Call site: services.ListLocations (services/public.go:285)
  SQL emitted: SELECT … FROM locations WHERE company_id=? AND device_id=? AND 
    recorded_at BETWEEN ?…? ORDER BY recorded_at DESC LIMIT 2000
  Notes: fast (uses composite index)
  ────────────────────────────────────────
  #: 7
  Call site: services.CountLocations (services/public.go:451)
  SQL emitted: SELECT COUNT(*) FROM locations WHERE …
  Notes: re-walks the same index range

  So a watch-mode poll is 7 round trips, 1 row lock, 1 write, and 2 correlated 
  subqueries against locations — to refresh data that conceptually only needs
  "give me the latest 2000 rows + a count".

  Recommended cuts (7 → 3)

  P1 — Drop ensureCompany from the read path. Saves queries #1, #2, #3 plus
  eliminates the write and lock. The dashboard doesn't provision; it reads.
  Registration (FindOrCreateDevice) and EnsureDashboardDevice already call
  ensureCompany, so companies still get created the moment a device first
  registers. Change: in ListCompanies (services/public.go:126), swap the
  ensureCompany call for findCompany, and return [] when nil instead of
  erroring. Or add a LookupCompany(org) that does a single read and bypass
  ListCompanies from buildDashboardData entirely (the dashboard only needs id, 
  company_token for one row).

  P2 — Merge ListLocations + CountLocations into one query. Postgres
  window-function count:
  SELECT …, COUNT(*) OVER () AS total_count
  FROM locations WHERE … ORDER BY recorded_at DESC LIMIT 2000
  Returns rows and a true total in the same round trip on the same
  locations_company_device_recorded index scan. Saves query #7.

  P3 — Rewrite ListDevicesInRange as a single query with one aggregation.
  Collapses #4+#5 and kills the two correlated subqueries:
  SELECT d.*,
         COALESCE(da.in_range, false) AS has_data_in_range,
         da.last_seen
  FROM devices d
  LEFT JOIN LATERAL (
    SELECT MAX(recorded_at)                                AS last_seen,
           BOOL_OR(recorded_at BETWEEN ? AND ?)            AS in_range
    FROM locations WHERE device_id = d.id
  ) da ON true
  WHERE d.company_token = ? AND d.company_id = ?
  ORDER BY COALESCE(da.in_range, false) DESC, da.last_seen DESC NULLS LAST, d.id
   ASC
  One round trip, one index scan per device, no per-device subselect cascade.
  This is the largest absolute latency win for tenants with lots of devices.

  Result: 3 calls — one company lookup, one devices+activity query, one
  locations+count query.

  Optional P4 — skip devices on watch-mode polls (7 → 2)

  The OOB swap of #device (partials/locations.html:78-80) is why devices are
  refetched on every poll. The device list only changes when (a) a new device
  registers, or (b) the date range changes. If the watch-mode poll drops the OOB
   device refresh — keeping it only on full page loads and form submits —
  ListDevicesInRange disappears from the hot path entirely. The trade-off: a
  brand-new device wouldn't appear in the dropdown until the user reloads.
  Probably acceptable.

  One independent issue worth flagging

  In watch mode without a date range (buildDashboardData server.go:474-479),
  CountLocations runs with no Start/End — that's a COUNT(*) over the device's
  entire history on every 10s poll. After P2 the window function bounds it to
  the 2000-row LIMIT scan, so it's no longer a separate concern. Pre-P2 it's
  worth being aware of.

  fetches for non-LIMIT rows. Not addressing now — it's a future optimization

  How it works

  The chart computes a label budget from the plot width (plotWidth / 80px
  minimum spacing ≈ 11 labels max for the 900px plot area), then walks a
  coarsening cadence list:

  ┌─────────┬────────────────────┬──────────────┐
  │ Cadence │     Bucket key     │ Label format │
  ├─────────┼────────────────────┼──────────────┤
  │ day     │ YYYY-M-D           │ Jun 9        │
  ├─────────┼────────────────────┼──────────────┤
  │ week    │ YYYY-M-D of Monday │ Jun 9        │
  ├─────────┼────────────────────┼──────────────┤
  │ month   │ YYYY-M             │ Jun 2026     │
  ├─────────┼────────────────────┼──────────────┤
  │ quarter │ YYYY-Q             │ Q2 2026      │
  ├─────────┼────────────────────┼──────────────┤
  │ year    │ YYYY               │ 2026         │
  └─────────┴────────────────────┴──────────────┘

  It picks the finest cadence whose bucket count fits within the label budget
  for the currently-visible columns, then emits one label + one column separator
   per bucket transition.

  What you'll see across span pills

  ┌───────────────────────┬───────────────────┬──────────────┬──────────────┐
  │         Span          │ Visible columns   │   Cadence    │   Labels     │
  │                       │      (rough)      │    picked    │   rendered   │
  ├───────────────────────┼───────────────────┼──────────────┼──────────────┤
  │ 1d                    │ 1–3               │ day          │ up to 3      │
  ├───────────────────────┼───────────────────┼──────────────┼──────────────┤
  │ 1w                    │ up to 7           │ day          │ up to 7      │
  ├───────────────────────┼───────────────────┼──────────────┼──────────────┤
  │ 1m                    │ up to 30          │ week         │ ~4–5         │
  ├───────────────────────┼───────────────────┼──────────────┼──────────────┤
  │ 6m                    │ up to 180         │ month        │ ~6           │
  ├───────────────────────┼───────────────────┼──────────────┼──────────────┤
  │ 1y                    │ up to 365         │ month        │ ~11          │
  ├───────────────────────┼───────────────────┼──────────────┼──────────────┤
  │ Full history (2 years │ up to ~730        │ quarter or   │ 2–8          │
  │  sparse)              │                   │ year         │              │
  └───────────────────────┴───────────────────┴──────────────┴──────────────┘

  Zooming in via the pills filters parsedSessions, which rebuilds the columns
  from the filtered set, which re-evaluates the cadence — so finer labels appear
   automatically as you narrow the window.

  Column separators got the same treatment in the same pass, so you also stop
  seeing hundreds of overlapping vertical hairlines in the wide view — only one
  separator per bucket boundary.
